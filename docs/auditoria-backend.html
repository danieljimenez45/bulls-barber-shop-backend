3. Arquitectura hexagonal

3.1 Fortalezas

  • Dominio aislado: ningún import de infrastructure, database, models ni schemas en app/domain/.
  • Puertos explícitos: IUserRepository, IBookingRepository, ITokenService, IPasswordHasher, IFileStorage, notificadores, etc.
  • Mapeo ORM → entidad en cada repositorio (ej. SQLAlchemyBookingRepository._to_entity).
  • Alembic apunta solo al ORM nuevo; .coveragerc excluye legacy de métricas.
  • Fábrica storage: app/infrastructure/storage/__init__.py → get_file_storage() (Cloudinary vs local).

Inconsistencia: cancelación / soft-delete de reservas

Archivo: app/infrastructure/persistence/repositories/booking.py (método delete, líneas ~111–125)

El soft-delete (B-22) fija deleted_at pero no cambia estado a "cancelada". is_slot_available filtra por deleted_at IS NULL y estado != "cancelada". Comportamiento funcional del slot: correcto vía _active(); semántica de negocio y export CSV pueden confundir.

Solución: En delete() llamar también orm.estado = "cancelada", o renombrar el puerto a soft_delete() y documentar en app/domain/booking/ports.py y use cases.

3.5 Inyección de dependencias

Patrón actual: composition root manual en cada handler.

repo = SQLAlchemyBookingRepository(db)
uc = CreateBookingUseCase(repo, notifier)
result = uc.execute(...)

Lo que existe:

  • app/database.py → get_db() (única dependencia compartida masiva)
  • app/api/dependencies/auth.py → get_current_admin
  • app/api/dependencies/pagination.py → PaginationParams
  • app/core/rate_limit.py → limiter(max_requests, window_seconds)
  • app/infrastructure/storage/__init__.py → get_file_storage()

Violación hexagonal estricta: routers importan clases concretas SQLAlchemy* de infrastructure, no solo puertos.

Solución opcional: Crear app/api/dependencies/composition.py con factories Depends(get_booking_repo), Depends(get_create_booking_uc), etc.

4. Auditoría de seguridad

4.1 Crítico — corregir antes de producción

4.1.1 Secretos y DEBUG por defecto

Archivo: app/config.py (líneas 9–17 aprox.)

DEBUG: bool = True
SECRET_KEY: str = "changeme-secret-key-in-production"
ACCESS_TOKEN_EXPIRE_MINUTES: int = 1440  # 24 h
DATABASE_URL: str = "sqlite:///./bulls_barbershop.db"

Archivo relacionado: app/main.py — docs_url y redoc_url solo ocultos si not settings.DEBUG.

Impacto: firma JWT predecible; documentación API expuesta; tokens falsificables.

Soluciones:
  • Añadir validación en Settings o al arranque: si entorno prod y SECRET_KEY contiene "changeme" → RuntimeError.
  • Forzar DEBUG=false en docker/docker-compose.prod.yml y documentar en docker/DOCKER.md.
  • Generar SECRET_KEY con openssl rand -hex 32 en despliegue.

4.1.2 Reseñas ocultas accesibles sin autenticación

Archivo: app/api/routers/reviews.py — GET /api/reviews/

Query param solo_visibles: bool = True sin Depends(get_current_admin) cuando es false.

Repositorio: app/infrastructure/persistence/repositories/review.py — filtra visible solo si solo_visibles=True.

Explotación: GET /api/reviews/?solo_visibles=false devuelve reseñas moderadas/ocultas.

Soluciones:
  • Opción A: Si solo_visibles is False, exigir admin: AdminUser = Depends(get_current_admin).
  • Opción B: Endpoint público solo con solo_visibles=true fijo; crear GET /api/reviews/admin protegido.
  • Añadir test: petición pública con solo_visibles=false debe devolver 401.

4.1.3 Servicios inactivos listables públicamente

Archivo: app/api/routers/services.py — solo_activos: bool = True en query público.

Test que lo documenta: tests/integration/test_services_api.py

Solución: Misma estrategia que reviews: JWT obligatorio para solo_activos=false.

4.1.4 Login sin rate limiting

Archivo: app/api/routers/auth.py — POST /login (líneas 16–38)

No usa Depends(limiter(...)). Contacto, bookings y reviews POST sí limitan.

Solución: Añadir Depends(limiter(max_requests=5, window_seconds=60)) al login. Considerar backoff exponencial o lockout tras N intentos por IP/email.
